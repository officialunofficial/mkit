# WP-M0-18: Ship `mkit-server` through `release.yml` (build matrix, signing, SBOM, provenance)

- **Milestone/track:** M0
- **Base:** `feat/mkit-server`; **branch:** `mkit-server/wp-m0-18-release-binary`
- **Depends on:** M0-10. Soft: M0-14, so the shipped binary includes the enc listener.
- **Size:** M (~200–400 lines of YAML, shell and docs)
- **Open-question dependency:** Q10 (default: the same 4 targets as `mkit`)

## Conventions

Same as WP-M0-01: TMPDIR, trailer, no CI polling. **Never push a tag or dispatch the release workflow.** Validate
statically and by local builds.

## Goal

Every signed release also publishes `mkit-server-<version>-<target>.tar.gz` next to `mkit-…tar.gz`. It must be
covered by the same cosign keyless signatures, the aggregated `SHA256SUMS` (+ signature), the SLSA provenance
attestation and the CycloneDX SBOM. Release notes and verification docs explain how to verify it.

## PRD refs

§5.1 ("It builds the `mkit-server` binary (D31): a signed release artifact next to `mkit`"), §8 M0 ("Ship the
`mkit-server` binary (D31) through `release.yml` (build matrix, signing, SBOM, provenance)"), D31.

## Scope

**IN:** `.github/workflows/release.yml` build, release and notes; `.github/workflows/release-verify.yml` (if it
enumerates archives); `docs/RELEASE.md`, `docs/INSTALL.md`; an optional `install.sh` note (don't add server install
to `install.sh` unless it's trivially generic); `scripts/validate-sbom.sh` (only if it asserts component names).

**OUT:** the container image (M0-19); crates.io publishing changes (per the adopted Q2 default, the `mkit-server*`

`publish = false` until then and `-worker` forever); npm. No release happens from `feat/mkit-server`: this WP only
wires the workflow, and the first run is WP-REL's tag.

## Edits

1. `build` job:
   - "Build release binary": **two separate cargo invocations** (review 01, B3 / R-65):
     1. `cargo build --release --locked --target $T -p mkit-cli --bin mkit --message-format=json-render-diagnostics > mkit-build.jsonl`
     2. `cargo build --release --locked --target $T -p mkit-server-native --bin mkit-server`

     Never `--bin mkit --bin mkit-server` in one invocation: cargo unifies features across every package selected in
     one build, so the shipped `mkit` would be compiled with hyper `server`, connectrpc `axum`/`zstd` and
     `mkit-server` `connect`/`sql` (and link SQLite), which breaks the server-free CLI (D31, Q1). Both invocations
     share `target/`; artifacts with different feature sets get different hashes, so nothing is overwritten. Add
     `SERVER_BINARY_NAME: mkit-server` to `env` (next to `BINARY_NAME` at ~53). `mkit-server` must build without
     protoc (vendored codegen, M0-06); keep the protoc install anyway.
   - **"Check release mkit artifact" (new step, right after invocation 1):** `scripts/check-release-artifact-features.sh
     mkit-build.jsonl target/$T/release/mkit` (new script) fails the build when the actual `mkit` artifact is not
     server-free. It checks what was really compiled, not a `cargo tree` model: from the `compiler-artifact` JSON
     messages of invocation 1 it collects every `(package_id, features)` and fails if any of `mkit-server-native`,
     `axum`, `rusqlite`, `libsqlite3-sys`, `tower-http` appears, if `hyper` was built with `server`, if `connectrpc`
     was built with `server` or `axum`, or if `mkit-server` was built with any feature outside the set `mkit-cli`
     declares for it (M0-13: `ssh`, `fs`; no `connect`, `sql`, `test-faults`); then a binary check: `nm`/`strings`
     on the stripped binary finds no `sqlite3_` symbol and no `x-mkit-test-` string. `scripts/check-cli-baseline.sh`
     (`cargo tree -p mkit-cli`) stays as the fast PR-time check, but it doesn't see unification in the release
     build, which is why this step exists.
   - New meta outputs: `server_archive=mkit-server-${VERSION}-${target}.tar.gz`,
     `server_stage=mkit-server-${VERSION}-${target}`.
   - "Stage server archive": copy `mkit-server`, `LICENSE-MIT`, `LICENSE-APACHE`,
     `rust/crates/mkit-server-native/README.md` (as `README.md`) and `CHANGELOG.md`.
   - Per-archive SHA256SUMS, `tar`, `.sha256` and cosign for the server archive. Refactor the sign and checksum
     steps into a loop over both archives rather than duplicating YAML, keeping each existing step's shell and
     flags exactly.
   - Upload: add the 5 server files to the same `build-<target>` artifact.
2. `release` job: confirm the `*.tar.gz` globs cover the server archives. Update the release body (≈605-640) with an
   "`mkit-server`" section: what it is (D31), how to verify (`cosign verify-blob … mkit-server-<v>-<t>.tar.gz`,
   `gh attestation verify`) and a link to the operator README.
3. `release-verify.yml`: if it downloads and verifies specific archive names (check around line 147, the "Alpine
   leg"), add the server archive for the Linux targets.
4. `docs/RELEASE.md` ("What gets published"), `docs/INSTALL.md` ("mkit-server" subsection).
5. `THIRD-PARTY-NOTICES`: ensure the notices cover the server binary's dependency set (rusqlite/SQLite, axum,
   tower-http, …). If `third-party-notices` runs cargo-about for `mkit-cli` only, extend it to both binaries (or the
   workspace) and dedupe.

## Acceptance criteria

- [ ] For each of the 4 targets, the build job produces, signs and uploads `mkit-server-<v>-<t>.tar.gz` (+ `.sha256`,
      `.sig`, `.crt`, `.cosign.bundle`).
- [ ] Provenance, aggregated SHA256SUMS and the GitHub Release include the server archives (globs verified, and
      changed only if needed).
- [ ] The SBOM and THIRD-PARTY-NOTICES cover the server's dependencies.
- [ ] Release notes and docs explain verification for `mkit-server`.
- [ ] actionlint is clean. A local release build of both bins succeeds.
- [ ] `mkit` and `mkit-server` are built by separate cargo invocations; `check-release-artifact-features.sh` runs on
      every target leg, passes on the real build and fails on the unified negative control (output in the PR).
- [ ] No tag pushed, no workflow dispatched.
- [ ] The release build never enables `test-faults` (grep the build step; `mkit-server --help` output contains no
      test flag, and a unit test in `mkit-server-native` asserts `cfg!(feature = "test-faults")` is false in the
      default feature set).

## Risks / gotchas

- The `aarch64-unknown-linux-gnu` leg runs on `ubuntu-24.04-arm`. rusqlite `bundled` needs a C compiler, which is
  present on the GitHub images. macOS cross-builds x86_64 from arm64 (`release.yml:210-212`), and cc handles it.
- `validate-release-tag` requires the tag commit to be reachable from `origin/main` (`release.yml:183`). The feature
  branch isn't released until merged to main; nothing to change here.
- Keep the build `--locked`. Refactoring the sign loop must not change cosign flags, which would break
  `release-verify.yml`.
