# WP-M0-11: S3 `BlobStore` (native) + fake S3 for CI; S3 + SQLite conformance

- **Milestone/track:** M0
- **Base:** `feat/mkit-server`; **branch:** `mkit-server/wp-m0-11-s3-blobs`
- **Depends on:** M0-10
- **Size:** M (~700–1000 lines)
- **Open-question dependency:** Q7 (an in-repo fake S3 in CI)

## Conventions

Same as WP-M0-01: TMPDIR, trailer, no CI polling, no proto change, a size check, workspace lints.

## Goal

Add an S3-compatible `BlobStore` to `mkit-server-native` (the `s3` feature, on by default in the binary). It reuses
the SigV4 signer from `mkit-transport-s3`. Wire it into `mkit-server serve --blob s3://…`, and prove the second
native exit combination: the storage suite and the full wire suite over **S3 + SQLite**, against an in-repo fake
S3 server in normal CI.

## PRD refs

§5.1 (`-native` "S3 blobs (reusing the SigV4 code from `mkit-transport-s3`)"), §5.3 (BlobStore: commit visible only
after BLAKE3 verification; put-if-absent), §8 M0 exit ("FS + SQLite and S3 + SQLite"), D2.

**IN:** `src/s3.rs` (`S3BlobStore`, `S3PackSink`); `s3` feature; binary flags; `mkit-server-conformance` `fake_s3`

## Files

- `rust/crates/mkit-server-native/Cargo.toml`:
  - `s3 = ["dep:mkit-transport-s3", "dep:reqwest"]`
  - `mkit-transport-s3 = { version = "0.4", path = "../mkit-transport-s3" }` (for `pub mod sigv4`,
    `mkit-transport-s3/src/lib.rs:37`)
  - `reqwest = { version = "0.13", default-features = false, features = ["rustls", "stream"] }` (async client;
    same major and TLS feature as the workspace)
  - default features become `["sqlite", "http", "s3"]`
- `src/s3.rs`:
  ```rust
  pub struct S3Config { pub endpoint: url::Url, pub bucket: String, pub prefix: Option<String>,
                        pub credentials: mkit_transport_s3::sigv4::Credentials }   // sigv4.rs:24 (carries region; redacting Debug)
  pub struct S3BlobStore { client: reqwest::Client, cfg: S3Config, clock: Arc<dyn Clock> }
  ```
  - key layout `"<prefix/><keyspace>/<64hex>"` with keyspace default `packs` (R-07), so the default is the same key
    shape as the R2 layout in `apps/vcs-worker/src/worker_impl/service.rs:92-94`
  - `begin`: sink spools to a `tempfile::NamedTempFile` while computing **both** BLAKE3 (identity) and SHA-256 (the
    SigV4 payload hash) incrementally, so memory stays bounded
  - `commit`: check len + BLAKE3 == key → `PUT` with `If-None-Match: *` and a streamed file body, signed with
    `sigv4::sign_request` (`sigv4.rs:215`)
    - 412 Precondition Failed → `AlreadyPresent`
    - 200 → `Created`
    - anything else → `StoreError::Unavailable` (redacted)
  - `get`: `GET` with an optional `Range: bytes=a-b` → `BlobBody::Stream` over `bytes_stream()`; 404 → `None`
  - `head`: `HEAD` → `content-length`
  - `probe`: `HEAD` on the bucket, or `GET ?list-type=2&max-keys=0`
  - `delete`: signed `DELETE`; 204/200 → existed per a preceding `HEAD` (S3 DELETE is idempotent and doesn't say),
    404 → `false` (R-06; unused until M5)
- `src/config.rs`: `--blob fs` (default) or `--blob s3://<bucket>[/<prefix>]` plus `--s3-endpoint`, `--s3-region`
  (default `auto`), and credentials from `MKIT_R2_ACCESS_KEY_ID`/`MKIT_R2_SECRET_ACCESS_KEY` (same env names as the
  client transport; `SPEC-CONFIG-SECURITY` lists them), or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` as a fallback.
  Credentials never come from repo-local config.
- `rust/crates/mkit-transport-s3/src/sigv4.rs`: **additive** `pub fn sign_request_with_payload_hash(creds, method,
  path, query, payload_sha256_hex: &str, endpoint, timestamp) -> SignedRequest`. Refactor `sign_request`
  (`sigv4.rs:215-263`) to call it with `sha256_hex(payload)`. Today's `sign_request` hashes the whole `&[u8]`, which
  would force buffering a 4 GiB pack in memory. The existing golden-vector tests must still pass unchanged. This is
  a published crate, so the new public fn is a minor, semver-compatible addition.
- `rust/crates/mkit-server-conformance/src/fake_s3.rs` (feature `fake-s3`, dev-only): an axum app keeping objects in
  memory. Supports:
  - `PUT` (honors `If-None-Match: *` → 412 if present)
  - `GET` (with `Range`, → 206)
  - `HEAD`, `DELETE` (the storage suite's `blob.delete_then_get_none` exercises it)
  - bucket probe

  It records requests for assertions and doesn't verify signatures. Unit tests elsewhere cover SigV4.
- `rust/crates/mkit-server-conformance/tests/s3_backends.rs`: the storage suite for `S3BlobStore` → `fake_s3`
- `rust/crates/mkit-server-native/tests/wire_s3_sqlite.rs`: the full wire suite, auth-v2 profile, over S3 (fake) +
  SQLite. **This is the M0 exit gate for "S3 + SQLite".**
- Optional: `tests/s3_minio.rs`, `#[ignore = "requires Docker (MinIO)"]`, gated on `MKIT_S3_MINIO=1`, via
  `testcontainers` (already a workspace dev-dep in mkit-cli)

## Acceptance criteria

- [ ] `wire_s3_sqlite` passes the full wire suite (exit gate). `s3_backends` passes every blob case.
- [ ] SigV4 is reused from `mkit-transport-s3::sigv4`, not copied. The new `sign_request_with_payload_hash` is covered
      by a test proving equality with `sign_request` on the same payload.
- [ ] A commit never makes bytes visible before BLAKE3 verification: the PUT is issued only after verification.
- [ ] The conditional PUT gives put-if-absent semantics. Identical re-puts return `AlreadyPresent`.
- [ ] Credentials come only from the CLI or env and are redacted from logs and `Debug`.
- [ ] Bounded memory during upload.

## Risks / gotchas

- S3 `If-None-Match` on PUT is supported by AWS S3 (since 2024) and R2. Older S3-compatibles may ignore it. Document
  that `--blob s3` requires conditional-write support.
- `reqwest` with `stream` needs `Body::wrap_stream` over a `tokio_util::io::ReaderStream`. Check that `tokio-util` is
  already in the graph (it is, via connectrpc and reqwest) before adding it.
- `sigv4::sign_request` takes a Unix timestamp. Feed it from the injected `Clock` so tests are deterministic.
- `mkit-transport-s3` pulls reqwest `blocking`. That's harmless in the native server, and the CLI doesn't gain
  anything new.
