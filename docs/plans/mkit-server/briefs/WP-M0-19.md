# WP-M0-19: `mkit-server` container image (multi-arch, signed, attested)

- **Milestone/track:** M0
- **Base:** `feat/mkit-server`; **branch:** `mkit-server/wp-m0-19-container-image`
- **Depends on:** M0-18
- **Size:** M (~200–350 lines: Dockerfile, YAML, docs)
- **Adopted defaults (Q9/Q10):** `ghcr.io/officialunofficial/mkit-server`, private while the repo is private, **no
  `latest` tag**; `gcr.io/distroless/cc-debian12:nonroot`; linux/amd64 + linux/arm64 (the Linux subset of the same
  targets as `mkit`); cosign keyless + GitHub provenance on the digest. The first image is pushed by WP-REL's release
  tag; the user then checks the package's visibility and repo link (human action).

## Conventions

Same as WP-M0-01: trailer, no CI polling. Never push a tag, dispatch the release workflow, or push an image from a
local machine.

## Goal

On every release, publish a minimal multi-arch container image of `mkit-server`, built **from the already-signed
release binaries** (not a separate compile). Sign the image digest with cosign keyless, attach build provenance and
an SBOM, and document verification and running it.

## PRD refs

§5.1 ("… plus a container image"), §8 M0 ("publish a container image"), D31.

## Scope

**IN:**
- `rust/crates/mkit-server-native/Dockerfile` (or `contrib/docker/mkit-server/Dockerfile`; choose one and document it)

**OUT:** Helm or compose files; publishing outside the release tag flow; Kubernetes manifests.

## Design

Dockerfile (binary provided by the build context):

```dockerfile
# syntax=docker/dockerfile:1
FROM gcr.io/distroless/cc-debian12:nonroot@sha256:<pinned-digest>
ARG TARGETARCH
COPY --chmod=0755 dist/${TARGETARCH}/mkit-server /usr/local/bin/mkit-server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/mkit-server"]
CMD ["serve", "--help"]
```

- glibc-linked binaries match distroless `cc`. Verify the dynamic deps with `ldd`: libc, libm, libgcc_s. rusqlite is
  statically bundled.
- `TARGETARCH` amd64 → `x86_64-unknown-linux-gnu`, arm64 → `aarch64-unknown-linux-gnu`.

`release.yml` job `container` (needs `[validate-release-tag, build]`; `permissions: contents: read, packages: write,
id-token: write, attestations: write`):

1. Download the `build-x86_64-unknown-linux-gnu` and `build-aarch64-unknown-linux-gnu` artifacts.
2. **Verify** each server archive's cosign bundle with `cosign verify-blob` and the same identity regexp the release
   notes document, extract it, and lay out `dist/amd64/mkit-server` and `dist/arm64/mkit-server`. This proves the
   image contains the signed bytes.
3. `docker/setup-qemu-action` + `docker/setup-buildx-action` (pinned by SHA like every other action in this repo),
   `docker/login-action` to ghcr with `GITHUB_TOKEN`.
4. `docker/build-push-action` with `platforms: linux/amd64,linux/arm64`, tags `ghcr.io/…/mkit-server:<version>`
   (and `:<major.minor>`; **no `latest`** until the repo is public, per Q9), `provenance: false` (step 6 uses GitHub's
   attestation instead), `sbom: false` (step 7 generates one), and outputs the digest.
5. `cosign sign --yes ghcr.io/…/mkit-server@<digest>` (keyless).
6. `actions/attest-build-provenance` with `subject-name: ghcr.io/officialunofficial/mkit-server`,
   `subject-digest: <digest>` and `push-to-registry: true`.
7. `anchore/sbom-action` on `image: …@<digest>` → `mkit-server-image.sbom.cdx.json`. Attach it with
   `cosign attest --type cyclonedx`, and upload it as a release asset (add it to the `release` job's download and
   `files:` list, and to SHA256SUMS).
8. The release notes get an image section with the digest (`needs.container.outputs.digest`) and the verification
   commands: `cosign verify ghcr.io/…@<digest> --certificate-identity-regexp … --certificate-oidc-issuer https://token.actions.githubusercontent.com`
   and `gh attestation verify oci://ghcr.io/…@<digest> -R officialunofficial/mkit`.

Order: the `release` job should `needs: container` so notes can include the digest. Weigh this against failure
isolation: if the image push fails, the binary release shouldn't be blocked. Pick one and justify it in the PR.
Recommended: `release` doesn't need `container`; a follow-up step in `container` edits the release notes via
`gh release edit`. That's allowed because it isn't a "comment", but confirm with the user.

## Acceptance criteria

- [ ] The Dockerfile is pinned by digest, runs non-root, and adds only the binary.
- [ ] The `container` job verifies the signed archives before building. The image is multi-arch, cosign-signed by
      digest, with provenance and an SBOM attestation.
- [ ] No `latest` tag while the repo is private (Q9).
- [ ] Docs cover pulling, running (`serve --listen 0.0.0.0:8080 --repo-root /data …`, volume and permissions) and
      verification.
- [ ] Dependabot covers the base image. actionlint is clean.
- [ ] The PR description restates the adopted Q9 defaults and the post-release visibility check.

## Risks / gotchas

- ghcr packages inherit repo visibility only when linked. Set the `org.opencontainers.image.source` label to the
  repo URL so the package links to the repo.
- `packages: write` must be scoped to the `container` job only.
- The first push of a **new** ghcr package from Actions fails unless the org allows GitHub Actions to create packages
  (org Settings → Packages). That's a human action before REL (00-plan §6, review 01 R-80); list it in the PR body.
- The distroless `nonroot` uid is 65532. Document the volume ownership for `--repo-root`.
