## Conventions

## Goal

`mkit serve <path>` keeps its exact wire behavior, but its engine becomes `mkit_server::ssh::serve_session` over
`FsBlobStore` + `FsLayoutStore`, driven by a **blocking executor** (`futures::executor::block_on`), so the CLI never
builds an async runtime. Close the SSH-SECURITY §4/§7 "slow-loris NOT mitigated" gap with a stdio idle timeout.
Turn the PRD's "tokio-free baseline" into the checked, accurate **server-free CLI** invariant.

## PRD refs

§4 ("`mkit serve` … hard-wired to `FileTransport` and has its own upload drain. The stdio mode has no read timeout;
SSH-SECURITY §4 and §7 list this as NOT mitigated"), §5.1 (`-native` row: the ssh/enc stdio loops call the same
pipeline through a blocking executor), §6.9, §8 M0 (production basics: ssh stdio read timeout; exit criterion

## Why the criterion is "server-free", not "tokio-free" (verified finding; adopted Q1 default)

`cargo tree -p mkit-cli -e normal -i tokio` shows tokio in the **default** CLI graph: via `mkit-transport-connect`
(unconditional client dependency with its own tokio runtime, `mkit-transport-connect/src/executor.rs`) and via
reqwest's blocking client. What the baseline actually guarantees is:

- (a) no axum, no hyper `server` feature, and no connectrpc `server`/`axum` feature
  (`cargo tree -p mkit-cli -e normal,features -i hyper` shows only client/http1/http2/default)
- (b) `mkit serve` creates no async runtime; it's blocking stdio I/O at `serve/mod.rs:201-207`

**The server-free CLI criterion** (used by every later WP that touches `mkit-cli`): the default-feature `mkit-cli`
normal dependency graph contains no `axum`, no `mkit-server-native`, no `rusqlite`/`libsqlite3-sys`, no hyper
`server` feature and no connectrpc `server`/`axum` feature, and `mkit serve` builds no async runtime. This WP encodes
(a) as `scripts/check-cli-baseline.sh` and keeps (b) by construction.

  New:
  ```rust
  pub(crate) fn serve_stdio(repo_root: &Path, input: Box<dyn Read + Send>, output: &mut dyn Write, idle: Option<Duration>) -> u8 {
      let pipeline = Pipeline::new(FsBlobStore::new(repo_root), FsLayoutStore::new(repo_root), Hooks::default(),
          PipelineConfig { auth: AuthMode::TransportIdentity, write_quota: None,
                           upload_limits: UploadLimits { max_total_bytes: MAX_BYTES_PER_CONN, max_chunks: MAX_FRAMES_PER_CONN }, .. },
          Arc::new(SystemClock), Arc::new(NoopMetrics))?;
      let mut src = StdioFrameSource::spawn(input, idle);   // thread: loop { read_frame(&mut r) → sync_channel(1) }
      let mut sink = StdioFrameSink::new(output);          // write_frame + flush
      match futures::executor::block_on(serve_session(&pipeline, Principal::SshForcedCommand { key: None }, &mut src, &mut sink, &cfg)) {
          SessionEnd::Clean => exit::OK, SessionEnd::ProtocolError | SessionEnd::Timeout => exit::PROTOCOL_ERROR, SessionEnd::IoError => exit::OK,
      }
  }
  ```
  `StdioFrameSource::next_frame` does a blocking `rx.recv_timeout(idle)` inside the future. Blocking is correct under
  `block_on`, since nothing else is scheduled.
  - `FrameError::LengthTruncated` → `Eof` (clean end, `serve/mod.rs:262`)
  - other parse errors → `Malformed`
  - timeout → `Timeout`: the session emits `Error{InvalidRequest, "idle timeout"}` best-effort and ends. The first
    frame (Hello) is also bounded.

  When the main thread returns, the process exits and the blocked reader thread dies with it. Don't try to join it.

## Risks / gotchas

- `read_frame` on `stdin.lock()` inside a spawned thread: `StdinLock` isn't `Send`. Lock inside the thread, or move
  `std::io::stdin()` in. Tests pass `Box<dyn Read + Send>` (`Cursor`).
- The shared `serve.lock` guard must be held for the whole session, since `serve_guard.rs` asserts it.
- `crates-publish.yml` runs `cargo publish --workspace`. `mkit-server` must be publishable (a README exists, the
  metadata is complete). Run `cargo package -p mkit-server --no-verify --allow-dirty` locally as a smoke check and
  include its output. It will fail if `generated/` is missing from the package, so check the `include`/`exclude`
  rules.
- The pipeline's `authenticate` for `TransportIdentity` takes `transport_principal` from the binding, not headers.
