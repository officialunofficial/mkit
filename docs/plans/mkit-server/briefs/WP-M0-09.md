# WP-M0-09: Shared SQL key-value backend (`SqlKvStore`) with versioned migrations; `mkit-server-native` crate with rusqlite

- **Milestone/track:** M0
- **Base:** `feat/mkit-server`; **branch:** `mkit-server/wp-m0-09-sql-stores`
- **Depends on:** M0-03, M0-04
- **Size:** M–L (~900–1200 lines; smaller than the earlier typed-table draft because all business logic lives in
  the M0-05a planners)
- **Reconciliation:** rewritten for the key-level storage contract (00-plan.md R-16..R-23). SQL is an internal
  detail of this backend; nothing above `NamespaceStore` sees it. Review 01: the transaction closure is an owned
  `'static` `FnOnce` (R-68), `NotAfter` is checked against the backend clock inside the transaction (R-61),
  `SQLITE_FULL` maps to `StoreError::Full` (R-83), and the native crate no longer enables `mkit-server/fs` (it moves
  to M0-10, R-71, so this WP needs nothing from M0-08).

## Conventions

Same as WP-M0-01: TMPDIR, trailer, no CI polling, no proto change, a size check, workspace lints.

## Goal

Implement the M0-02a `NamespaceStore` contract **once** over SQLite, in `mkit-server` behind a `sql` feature, on a
tiny synchronous `SqlConn` trait. Durable Object SQLite (M0-16) and rusqlite (here) both implement `SqlConn`, so the
native SQLite backend and every per-partition DO run the same code and the same physical migrations. Create
`mkit-server-native` with the rusqlite `SqlConn` and run the storage suite (including crash/restart) against it.
Because `ContentIndex` is a layer over `NamespaceStore` (M0-02b), this backend provides it for free.

## Design

```rust
// mkit-server/src/sql/mod.rs — sync on purpose: DO SQL exec and transactionSync are synchronous; rusqlite is synchronous.
#[derive(Debug, Clone, PartialEq)] pub enum SqlValue { Null, Integer(i64), Text(String), Blob(Vec<u8>) }
pub type Row = Vec<SqlValue>;
#[derive(Debug, thiserror::Error)] pub enum SqlError { #[error("sql backend error")] Backend(crate::error::Redacted), #[error("constraint")] Constraint, #[error("corrupt row")] Corrupt(&'static str) }
/// A cheaply cloneable handle (rusqlite: `Arc<Mutex<Connection>>`; DO: `Rc<State>` + the storage JsValue).
pub trait SqlConn: MaybeSend + MaybeSync + Clone + 'static {
    fn exec(&self, sql: &str, params: &[SqlValue]) -> Result<u64, SqlError>;
    fn query(&self, sql: &str, params: &[SqlValue]) -> Result<Vec<Row>, SqlError>;
    /// Run `f` atomically and synchronously. MUST NOT be implemented with BEGIN/COMMIT strings: Durable Objects reject
    /// them and require storage.transactionSync. rusqlite uses Connection::transaction. `f` never awaits, which is
    /// what makes `apply` cancellation-safe (M0-02a rule 4).
    ///
    /// Review 01 (R-68): the closure is OWNED and 'static. The DO bridge (`transactionSync`) wraps it in a
    /// wasm-bindgen `Closure`, which must be 'static (see `apps/mkit-worker-common/src/replay.rs:75-94`, which needs
    /// `FnOnce + 'static`), and mkit-server forbids `unsafe`, so a borrowed `&mut dyn FnMut` can't cross the bridge.
    /// The implementation passes a clone of the connection handle into `f`; `apply` moves the owned `Batch` (and the
    /// clock reading) into the closure.
    fn transaction<T: 'static>(&self, f: Box<dyn FnOnce(Self) -> Result<T, SqlError> + 'static>) -> Result<T, SqlError>;
    /// The backend's own clock for `NotAfter` (M0-02a rule 8): native = system clock, DO = the Durable Object's
    /// `Date.now()` (which advances with I/O, so it reflects the request's arrival at the DO).
    fn now_ms(&self) -> u64;
}
```

Physical schema v1 (every statement must run on rusqlite and DO SQLite: no `ATTACH`, no `PRAGMA` in migrations):

```sql
CREATE TABLE IF NOT EXISTS mkit_schema (id INTEGER PRIMARY KEY CHECK (id = 1), version INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS kv (part TEXT NOT NULL, key BLOB NOT NULL, value BLOB NOT NULL,
                               PRIMARY KEY (part, key)) WITHOUT ROWID;
```

- `part` is the `Partition` encoding, so one native file holds every partition: this is the D34 shard model on
  SQLite, "tables keyed by shard" (reconciliation R-29). A DO holds exactly one partition and the column is constant
  there. Native SQLite is single-writer across all shards; scaling a native deployment past one writer is the future
  Postgres backend (D2), not this WP.
- `migrate()` reads `mkit_schema.version`. A newer version than the binary's is an error (refuse; no downgrade).
  It applies each missing migration inside `transaction`, then bumps the version. Logical layout changes (new key
  classes) need **no** physical migration; the M0-02a layout-version key handles them.

`SqlKvStore::apply(p, batch)` runs in **one** `transaction` (reconciliation R-16):
1. size checks (`MAX_KEY_BYTES`, `MAX_VALUE_BYTES`) before opening the transaction
2. inside the transaction closure, read `conn.now_ms()` once, then each precondition in order: `NotAfter(d)` →
   `now_ms > d` fails (observed = be64(now_ms)); key preconditions → `SELECT value FROM kv WHERE part=?1 AND key=?2`;
   the first failure returns `PreconditionFailed{index, observed}` and the transaction is rolled back (nothing
   written)
3. each write: `INSERT INTO kv(part,key,value) VALUES(?,?,?) ON CONFLICT(part,key) DO UPDATE SET value=excluded.value`
   or `DELETE FROM kv WHERE part=? AND key=?`

One statement per precondition and per write keeps every statement ≤ 3 bound parameters and far below the DO limits
(100 bound parameters, 100 KB statements, 2 MB rows). `get_many` issues `SELECT … WHERE part=? AND key IN (…)` in
chunks of ≤ 64 keys. `stats(p)` = `SELECT COUNT(*), SUM(length(key)+length(value)) FROM kv WHERE part=?`, cached for
60 s per partition (DO: `storage.sql.databaseSize` instead; the DO holds one partition). `scan` is `SELECT key, value FROM kv WHERE part=? AND key >= ? AND key < ? [AND key > ?cursor]
ORDER BY key LIMIT ?`.

Capabilities: `{ atomic_multi_key: true, key_classes: All, membership: StorePresence, implicit_layout_version: None }`
(M1 flips membership to `Explicit` when WP-1.7 adds the membership layout).

Errors: an `SQLITE_FULL` result (rusqlite `ErrorCode::DiskFull`; on a DO the exception message contains
`SQLITE_FULL`, M0-16) maps to `StoreError::Full`; reads and deletes are unaffected (M0-02a rule 7, 00-plan P-24).
`SqlError` gains a `Full` variant for this.

`RusqliteConn`: `Arc<Mutex<rusqlite::Connection>>` (cloneable; recover from poisoning); `now_ms` = `SystemTime`. Open with `journal_mode=WAL`,
`busy_timeout=5000`, `synchronous=FULL` (refs must be as durable as today's fsync'd files). Run `migrate` at open.
`transaction` uses `transaction_with_behavior(Immediate)`.

`Blocking<S>` (native): wraps `Arc<S>` and runs each call in `tokio::task::spawn_blocking`. The blocking task runs
to completion even if the awaiting future is dropped, which preserves cancellation safety. It is generic, so M0-10
uses it to wrap `FsBlobStore`/`FsLayoutStore` for the tokio server once it enables `fs`; this WP tests it only over
`SqlKvStore<RusqliteConn>`.

## Acceptance criteria

- [ ] One SQL implementation of the contract. `mkit-server` has no rusqlite dependency, and `sql` compiles for wasm32.
- [ ] `SqlConn::transaction` takes an owned `'static` `FnOnce`; no `unsafe` anywhere.
- [ ] `mkit-server-native` does not enable `mkit-server/fs` in this WP.
- [ ] Storage suite: zero failures; zero skips on the file-backed store (durability included).
- [ ] No `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` string anywhere in `mkit-server/src/sql/` (a test greps it).
- [ ] Every statement stays within the DO limits (≤ 100 bound parameters; a test asserts the max over all generated
      statements, including `get_many` chunks).
- [ ] Physical migrations are versioned, forward-only and idempotent, and refuse newer schemas.
- [ ] The native README documents physical and logical backup and restore.
- [ ] `cargo deny` passes with rusqlite bundled.
- [ ] The CLI graph is unaffected (`cargo tree -p mkit-cli -e normal | grep -E 'rusqlite|libsqlite3'` is empty).

## Risks / gotchas

- DO SQL binds `ArrayBuffer`/`Uint8Array` blobs. Keep values to Integer/Text/Blob/Null.
- Ordering: `ORDER BY key` on a BLOB column is memcmp order in SQLite, which is the byte order the contract
  requires. Pin it with the `kv.scan_byte_order` case.
- rusqlite `bundled` compiles C (cc). That's fine natively and never reaches wasm or the CLI.
